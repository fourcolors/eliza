## 2. Project Goals & Key Objectives
See: [Project Goals](goals.txt) for complete details.

1. **Cross-Chain Communication**
   - Integrate Hyperlane message passing for cross-chain calls.
   - Provide robust event/status tracking and payload integrity checks.

2. **Warp Routes & Asset Transfer**
   - Implement Warp Route logic for seamless cross-chain token moves.
   - Offer a clean API for these transfers, with thorough status checks.

3. **New Chain Deployment**
   - Automate scripts for validator & ISM deployment to new chains.
   - Provide a step-by-step setup guide (ensuring consistent security).

4. **Functional (Pure) Design**
   - Use immutable data structures and avoid side effects.
   - Keep functions pure and composable.
   - Isolate side effects to specific boundaries.
   - Follow established design patterns.

5. **Error Handling & Recovery**
   - Validate inputs pre-cross-chain calls.
   - Implement retry/rollback for failed ops.
   - Provide structured logs for debugging.
   - Handle edge cases thoroughly.

6. **Testing & Verification**
   - Write unit tests before implementation.
   - Use vitest for all testing.
   - Cover edge cases and error paths.
   - Achieve high test coverage (≥85%).
   - Include integration tests for cross-chain flows.

7. **Documentation & Configuration Guide**
   - Maintain dev-friendly docs on usage, `.env` setup, common pitfalls.
   - Keep code, docs, and examples aligned.
   - Document design decisions and rationale.

8. **Performance Optimization**
   - Reduce on-chain overhead, optimize cross-chain throughput.
   - Audit gas usage for bridging and warp route calls.
   - Use efficient data structures and algorithms.

9. **Security Enhancements**
   - Integrate Hyperlane security modules.
   - Validate messages to prevent replay attacks.
   - Provide best practices for private key handling.

10. **Maintainability & Future-Proofing**
    - Use modular, functional programming approach.
    - Keep modules pure and side-effect free.
    - Maintain stable APIs.
    - Follow framework conventions.

## 3. Implementation Guidelines
See: [Commit Reviewer Guidelines](commit-reviewer.txt) for detailed code quality and security requirements.

### Development Flow
1. **Pre-Implementation**
   - Read ALL relevant documentation first.
   - Write test cases before implementation.
   - Plan functional approach.
   - Review commit-reviewer.txt checklist.

2. **Implementation**
   - Follow functional programming principles:
     * Use immutable data structures
     * Avoid side effects
     * Write pure functions
     * Apply design patterns
   - Adhere to commit-reviewer.txt for:
     * Code quality standards
     * Security requirements
     * Performance guidelines
     * Testing requirements

3. **Post-Implementation**
   - Run full test suite with vitest.
   - Run pnpm build.
   - Update documentation.
   - Submit for review using commit-reviewer.txt checklist.
   - Follow git-commit.txt guidelines for commit messages.

### Version Control Guidelines
See: [Git Commit Instructions](git-commit.txt)

Commit Types:
- feat: New features
- fix: Bug fixes
- docs: Documentation changes
- style: Code style changes
- refactor: Code refactoring
- perf: Performance improvements
- test: Test updates
- build: Build system changes
- ci: CI configuration changes
- chore: Maintenance tasks

Example:
```
feat(messaging): implement cross-chain message verification

- Add message verification using Hyperlane ISM
- Implement signature validation
- Add rollback mechanism

Closes #123
```

### Problem Resolution
- **Security Issues**: Fix immediately, update dependencies if needed.
- **Code Quality Issues**: Address per commit-reviewer.txt; ensure tests are updated.
- **Package Updates**: Always ask before updating versions, verify compatibility.
- **Edge Cases**: Double check all edge cases in implementation.

## 6. Environment Configuration Management

### Initial Setup
```bash
# Copy example env file
cp .env.example .env
```

### Configuration Categories
1. **Chain Configuration**
   - RPC endpoints
   - Contract addresses
   - Network-specific settings

2. **API Keys**
   - Provider keys
   - Explorer API keys

3. **Gas Settings**
   - Multipliers
   - Price limits
   - Chain-specific overrides

4. **Security**
   - ISM configurations
   - Validator settings
   - Key management

### Update Triggers
- Adding new chains or modifying existing ones
- Changing RPC providers or contract addresses
- Adjusting gas settings or security keys

### Validation Steps
After updating .env:
```bash
# Verify environment loading
pnpm test:env

# Check chain connections
pnpm test:chains

# Verify contract access
pnpm test:contracts
```

### Troubleshooting
If environment issues occur:
- Check variable names match .env.example
- Verify RPC endpoints are accessible
- Confirm API keys are valid
- Check contract addresses exist
- Verify environment is loaded

## 9. Step Progression & Decision Making

### When to Commit
Commit when you have:
1. Completed a logical unit of work
2. Added new functionality with tests
3. Fixed a bug with regression tests
4. Updated documentation that stands alone
5. Made significant refactoring changes

Do NOT commit when:
- Tests are failing
- Documentation is incomplete
- Changes span multiple unrelated features
- Commit message cannot clearly describe changes

### When to Request Review
Request review when:
1. Feature implementation is complete
2. All tests pass
3. Documentation is updated
4. Code meets quality gates
5. Changes follow functional principles

Skip review for:
- Minor documentation fixes
- Test-only changes
- Development-time configuration updates

### When to Progress Steps
Check current step file (e.g. `step1.txt` through `step16.txt`) for:
1. Current step requirements and goals
2. Dependencies on other steps
3. Required approvals or signoffs

Progress to next step when:
1. Current step implementation meets checklist requirements
2. All tests pass
3. Documentation is complete
4. Required reviews are approved
5. No blocking issues remain

Block step progression if:
1. Previous step has failing tests
2. Required documentation is missing
3. Dependencies are not met
4. Security issues are unresolved

### Reference Files
Essential files to check:
- `stepN.txt`: Current step definition and requirements (N = 1-16)
- `implementation-checklist.md`: Required implementation criteria
- `commit-reviewer.txt`: Code quality and review requirements
- `git-commit.txt`: Commit message standards
- `goals.txt`: Overall project goals and milestones

Always validate against:
1. Implementation checklist requirements
2. Integration points from current step
3. Security considerations
4. Performance requirements
5. Testing criteria
